# 実装前チェック手順（シオン案 v0.3）

## 0. この文書の位置づけ

- 対象：新しいツールの新設、または既存ツールの「保存形式・状態・計算式」に触る大きな機能追加
- 対象外：既存パターンにそのまま乗る設定判別チェッカーの追加（従来の標準工程1で足りる）
- 工程上の位置：ARCHITECTURE.md §5 の待ち行列に載った項目を「仕様書」にする前の段階
- 成果物：「骨格書」（§6）。骨格書が実装ゲート（§4）を通ってから仕様書を書く

### 全体の工程（新ツール・大きな機能）
1. 待ち行列（ARCHITECTURE.md §5）から着手項目を決める
2. 出典照合 → **本手順で骨格書を作る** → 夢爽の裁可
3. 仕様書作成（AGENTS.md §9-72・§9-73 の記載要件を満たす）→ ツムギ宛の指示書
4. ミコト実装 → シオンが raw で裏取り → 修正ループ
5. limited 公開 → 実機テスト → フィードバック反映 → 正式公開
6. §9-53 の棚卸し（ルール化候補の提示と裁可）

本書が扱うのは 2 の中身。3 以降の規約は AGENTS.md に従う。

## 1. 基本方針（5原則）

1. **実装より下準備**
   曖昧なまま実装に入ると、直す場所が「コード」ではなく「設計」になり手戻りが大きい。
   デバッグで見つかる問題の多くは、実装前に定義で防げる。
2. **流れを先に一本通す**
   最初から細部を決めない。通常時→契機→当たり→AT→終了→次の通常時、と
   実際に起きる順で最初から最後まで書き出す。
3. **変えにくいものから決める**
   区切り・状態・引き継ぎ・保存・計算元は、後から変えると影響が全体に及ぶ。ここを優先する。
4. **曖昧さと認識ズレは実装前に見つける**
   「具体例が書けないルール」は曖昧なルール。質問リストにして夢爽に確認する。
5. **例外と見た目は後から足す**
   異常ケース・細かいUI・文言は直しやすい。実機テストで出たものから追加する。

## 2. 工程（Step 0〜5）

### Step 0：目的と対象の確認
- 何を「記録」し、何を「振り返り」で見るか（二層構造のどちらに何を置くか）
- 既存ツールとの関係：新設か、rec/index.html の機種定義追加か、kado-note 側の対応が要るか
- 出典：ちょんぼりすたに載っている挙動と、実機のメニュー・サブ液晶・履歴で確認できるもの
- 出典にない挙動は推測で設計に入れない（ARCHITECTURE.md §2-1）。夢爽に確認する（未確認は「未確認」と明記）

### Step 1：流れの洗い出し（考え方：Domain Storytelling / EventStorming）
実戦で起きることを、時系列で一文ずつ書く。「誰が・何をして・何が起きる」の形。

例（からくりサーカス2の骨格レベル）
1. 通常時を回す（周期カウント進行）
2. 周期到達 → CZ抽選 → 当選 or ハズレ
3. CZ → AT当選 or 失敗して通常時へ
4. AT開始（初期枚数・上乗せ）
5. AT終了 → 引き戻しゾーン → 通常時へ

チェック
- 最初（着席・開始時入力）から最後（離席・終了時入力）までつながっているか
- 「戻る」流れ（失敗して通常時へ、など）が書けているか
- 各出来事に「プレイヤーが入力する必要があるか／台から読めるか」を付ける

### Step 2：区切りと状態の定義（考え方：状態遷移）
- 状態の一覧（通常時・CZ・AT・引き戻し・閉店前 など）
- 各状態の「開始条件」と「終了条件」
- 同時に成立する状態があるか（例：AT中も周期カウントが進むか）
- 状態が変わるときに「区切り」として記録するか（ログの1行になるか）
- 取り消し・巻き戻しの単位。状態を戻すときは判定ロジックの範囲も一緒に戻す（§9-68）

成果物：状態遷移表（現在の状態 × 出来事 → 次の状態）

### Step 3：引き継ぎ・保存・計算元の定義（最重要）
**引き継ぎ**
- 状態をまたいで残る値／リセットされる値（周期カウント、差枚、獲得枚数など）
- 日またぎ・セッションまたぎで残す値

**保存**
- 一次データとして保存する値（入力そのもの）
- 保存しない値（導出値。例：lendRate と exchangeRate は別々に持ち、換算結果は保存しない）
- エンベロープ／payload の切り分け（規約は ARCHITECTURE.md §4.1・docs/session-schema-v2-design.md を正本とし、本書では再定義しない）
- sessionId・注釈レイヤー・公開レイヤーの扱いは ARCHITECTURE.md §4.2〜4.4 に従う
- 版数（ver / schemaVer）の上げ方・旧データの読み方は §9-59 に従う

**計算元**
- 画面に出す値ごとに「計算式」と「入力元」を1つに決める（§9-84・作業規約8：分母定義は1関数に集約）
- 実測がない値は推計値で埋めず「—」を出す（§9-84）
- 分母の性質を確認する（通常時のみか、AT込みか）。解析値と条件が違う分母では 1/x を出さない（§9-70）
- 判別項目ごとに有効区間が違うなら分母を分離する（§9-66）

### Step 4：曖昧箇所の洗い出し（考え方：Example Mapping）
- 主要なルールごとに具体例を最低1つ書く
  - 例：「AT中に閉店」→ 終了時入力はどう扱うか
  - 例：「CZ中に台移動」→ セッションはどう区切るか
- 例が書けない、または人によって答えが変わりそうなものを「質問リスト」にする
- 質問リストを夢爽に提示し、決定 or 「未定（実装後に決める）」に振り分ける

### Step 5：実装ゲート判定
§4 のチェックリストで判定する。通らなければ Step 1〜4 に戻る。

## 3. 先に決めるもの／後で決めるもの

| 先に決める（変えにくい） | 後で決める（直しやすい） |
|---|---|
| 状態の一覧と遷移の契機 | ボタンの配置・色・サイズ |
| 区切り（ログ1行になる単位） | 文言・ヒント表示・トースト |
| 保存する値／しない値、payload の項目名 | 参照タブの中身 |
| 各表示値の計算式と入力元 | カードの見た目・グラフ種別 |
| 引き継ぎ・リセットの規則 | 異常ケースの細かい挙動 |
| ID・時刻の扱い（sessionId / t） | 削除・訂正の操作手順 |
| タブ構成の骨格（5以内・§9-67） | タブ内の並び順 |
| 公開レイヤー（保存＝完全体／出力＝サブセット） | 共有テンプレの文面 |

判断基準：**その変更で保存済みデータやほかのツール（kado-note 等）が影響を受けるか**。受けるなら「先に決める」。

## 4. 実装ゲート（チェックリスト）

以下がすべて揃ったら仕様書に進んでよい。

- [ ] 流れが最初から最後まで一本で書けている（戻りの流れも含む）
- [ ] 状態遷移表がある（状態 × 出来事 → 次の状態）
- [ ] 保存する値／しない値が決まっている
- [ ] 画面に出す値ごとに、計算式と入力元が1つに決まっている
- [ ] 分母の性質（通常時のみ／AT込み）を確認した
- [ ] 主要ルールに具体例が1つずつある
- [ ] 夢爽への質問リストが空、または残りは「実装後に変えても保存データに影響しない」ものだけ
- [ ] 共通ファイル（checker-bayes.js・kado-note・店舗マスタ等）に触るかどうかが判明している
- [ ] 出典にない挙動を推測で入れていない（未確認は「未確認」と明記）

通らない場合：不足している Step に戻る。

**保留付き通過（夢爽裁可済み）**
保留項目があっても、以下を骨格書に明記すれば通過できる。
- 保留項目の一覧
- 各項目の影響範囲（保存データ・共通ファイル・他ツールに影響しないこと）
- 決定予定の時期（実機テスト後 など）
保存データや共通ファイルに影響する項目は保留にできない。

## 5. 実装後に詰めるもの

- limited 公開 → 夢爽の実機テスト（AQUOS Sense9・390px）→ フィードバック反映 → 正式公開
- 実機テストで出た例外・異常ケースを追加する（先回りで全部は作らない）
- 実機テストの定番確認：ボタンの押しやすさ・画面の縦の長さ・カードの文字はみ出し・共通ファイル変更時は既存機種1つのカード確認
- 例外を追加した結果、状態や保存形式に影響が出た場合は Step 3 に戻り、§9-59 に従って版数の扱いを決める（UIのみの変更では上げない）

## 6. 骨格書テンプレ

仕様書の前に、以下の項目で骨格書を作る。埋まらない項目は「未定」と書く（空欄にしない）。

1. 目的と対象（Step 0）
2. 出典と実機で確認できるもの
3. 流れ（時系列の一文リスト）
4. 状態遷移表
5. 引き継ぎ・リセット規則
6. 保存する値／しない値（エンベロープ／payload）
7. 表示値ごとの計算式と入力元
8. 具体例と質問リスト（決定／未定の振り分け）
9. 先に決める／後で決めるの振り分け結果
10. 実装ゲート判定結果と保留項目

## 7. 手法の使い分け（早見表）

| 手法 | 何を見つけるためか | 使う工程 | 平易に言うと |
|---|---|---|---|
| Domain Storytelling | 実戦の流れと登場する要素 | Step 1 | 「実際にホールで何が起きるか」を物語として書く |
| EventStorming | 出来事と、その順序・分岐 | Step 1 | 出来事を付箋のように並べて順番と分かれ道を見る |
| 状態遷移 | 状態の区切りと切り替わる条件 | Step 2 | 「今どの状態か」と「何で次に移るか」を表にする |
| Example Mapping | ルールの曖昧さ・例外 | Step 4 | ルールごとに例を書いて、書けないところを洗い出す |

全部を毎回使う必要はない。**流れ→状態→保存と計算→具体例** の順で、足りない視点を補う道具として使う。
