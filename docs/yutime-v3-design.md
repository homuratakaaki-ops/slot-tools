# 遊タイム実戦ツール v3 設計図

作成: シオン

依頼者: 夢爽

実装対象: `yutime-v3.html`
公開形態: 限定公開。TOPページ・既存ページからリンクしない。URL直打ちのみ。

## 0. 開発方針

- v3 は現行 v2 とデータを共有しない。
- localStorage キーは `ytv3:` prefix に完全分離する。
- 現行 `yutime-record.html` は残置し、v3 安定後に移行ツールを別途検討する。
- SPA 構成は現行と同じく、単一 HTML・インライン JS とする。
- スキーマ変更時の容量予算記録ルールを v3 にも適用する。
- 縦に長い・情報が過密・選別が目的のセクションは既定で折りたたむ。開く手間より、見ないものをスクロールする手間の方が高くつくため。
- テキスト列とボタン群の横並びグリッドは、ボタン合計幅が画面幅を超えうる場合は縦積みにする。min-content潰れによる縦書き化を防ぐため。
- **使う人が『いま自分は何をしているか』を常に分かる状態にする。迷わせない。——以下の原則（テキストに逃がした情報は無いのと同じ／判断の場に前提を置く／実機と照合できる／先に条件・後に値／ウィザード廃止）はすべてこの具体策である**
- **入力・判断する場所では、いまどの台の・どの状態を扱っているかを、その場で実機と照合できるようにする。照合に不要な情報は置かない。** 検査方法：その画面のスクショ1枚を他人に見せて「どの台の・どの状態の・何の話か」が分かること。（B94）

### 値の出典は1つにする

新しい値を画面に出すとき、その値が既にどこかで計算されていないかを先に確認する。
同じ意味の値を2つの経路から取ると、片方だけ直したときに表示が食い違い、しかも気づきにくい。

- 同じ意味の値は1つの関数から取る。画面ごとに計算を書き足さない
- フォールバックの優先順位も、その1関数の中に置く
- 推計値・理論値を実測値の代わりに使わない。実測が無ければ「—」を出す

（S5までに、消費玉・獲得出玉・合計R数・1R当たり・実測出玉の5系統でこの型の不整合が発生し、
すべて出典の一本化で解消した）

## 1. 実戦フロー

```text
[店選択] -> [フロアマップ（台を探す）] -> 台番タップ
                              -> [打ち始めウィザード] -> セッション開始
                              -> [稼働中画面]
                              -> [当選ウィザード]
                             -> [ヤメ入力] -> セッション確定 -> マップへ戻る
```

- 全ウィザードは「次へ」で進む直列形式。
- 全項目スキップ可能。
- スキップ項目は `null` 保存する。
- 未入力項目があるセッションは「未入力あり」バッジを表示し、台帳の「記録の修正・削除」から後で補完できる。

## 2. データモデル

### 2.1 Store

```json
{
  "id": "string",
  "name": "string",
  "isPersonal": true,
  "lendRate": 4,
  "exchangeBalls": 25,
  "createdAt": "ISO8601"
}
```

- `lendRate` は貸玉レート（円/玉）。現金投資の玉換算に使う。
- `exchangeBalls` は交換玉数（100円あたり）。25玉交換なら25、28玉交換なら28を入れる。
- 換算収支は `差玉 * (100 / exchangeBalls)` で計算する。
- 店フォームは店名、パーソナル有無、貸玉レート、交換玉数だけを扱う。期待値用の純払い出し量・時短消費率・推定回転率は店属性ではないため保存しない。
- 既存店は読み込み時に `lendRate: 4`、`exchangeBalls: 25` を補完する。旧 `exchangeRate` がある場合は `100 / exchangeRate` で `exchangeBalls` へ自動変換する。

### 2.2 MapLayout

店に複数持てる。B13以降は機種・コーナー単位の名前付きマップとして扱い、島ビルダーで入力した構造化データを保存する。

```json
{
  "maps": [
    {
      "id": "map_main",
      "name": "P大海物語5スペシャル",
      "islands": [
        {
          "name": "大海入口島",
          "left": { "from": 101, "to": 105 },
          "right": { "from": 199, "to": 195 },
          "gaps": { "left": ["103"], "right": ["197"] },
          "leftPresetId": "umi-sp5",
          "rightPresetId": "umi-sp5",
          "excluded": ["104"]
        }
      ],
      "assumedRate": 16.5,
      "updatedAt": "ISO8601",
      "errors": []
    }
  ],
  "activeMapId": "map_main"
}
```

- `left` は左列、`right` は右列。右列が空欄の場合は `null` として片面島を表す。
- `from` と `to` は昇順・降順どちらでもよい。
- `excluded` は存在しない台番の一覧。プレビュー上の台番をタップして除外/復帰する。
- `name` は島の任意名。空欄の場合は、列機種プリセットが同一または片面島なら機種名、判定できなければ「島N」を表示する。
- `gaps.left` / `gaps.right` は物理区切りの位置。指定した台番の後ろに空白スペーサーと柱マークを表示する。連続入力の遷移順には影響しない。
- `leftPresetId` / `rightPresetId` は列単位の機種プリセット。未設定台への一括適用と、遊タイム機能の出し分けに使う。
- `assumedRate` はそのマップ（機種・コーナー）の推定回転率。台帳データがない台の期待値判定に使い、店単位では保存しない。
- 旧テキスト定義 `{ source: "100-104 | 199-195" }` は読み込み時に `islands` へ自動変換する。
- 旧テキストに歯抜け指定がある場合は、先頭から末尾までの範囲に展開し、存在しない中間台を `excluded` に入れて台番構成を維持する。
- 重複台番など、読めても危険な状態は警告表示する。

### 2.2.1 PresetSettings

```json
{
  "umi-sp5": {
    "netBallsPerWin": 1400,
    "netBallsPerWinManual": false,
    "jitanNormalBallsPerSpin": 0,
    "jitanFastBallsPerSpin": 0,
    "yutimeBallsPerSpin": -0.3
  }
}
```

- `presetSettings` は機種プリセット単位の手動設定を保存する。
- B52改訂2以降、`netBallsPerWin` は大当たり1回あたりの純払い出し量（ラウンド数×出玉）とし、時短中の玉増減は含めない。既定はプリセット定義の1400。
- `netBallsPerWinManual` は手入力上書きフラグ。true の場合だけ `netBallsPerWin` を最優先し、false の場合は当選記録から自動算出する。
- `jitanNormalBallsPerSpin` は100回転時短、`jitanFastBallsPerSpin` は200回転時短、`yutimeBallsPerSpin` は遊タイム消化の1回転あたり玉増減。負の値は消費、0は消費なし。
- 店をまたいで同じ機種プリセットに共通適用する。実測出玉からの自動切替は行わない。

### 2.3 Machine

```json
{
  "id": "string",
  "storeId": "string",
  "daiNo": "string",
  "modelName": "string",
  "roundBalls": null,
  "memoEntries": [],
  "nailRating": { "yori": null, "michi": null, "nekase": null, "through": null, "warp": null },
  "presetId": "",
  "evSupported": false
}
```

- フロアマップから台番だけの Machine を自動生成する。
- 機種名、1R 玉数、台メモ（釘・癖など）は後付け編集できる。
- `nailRating` は台単位の釘・ネカセ評価。`yori`（寄り）、`michi`（道）、`nekase`（ネカセ）、`through`（スルー）、`warp`（ワープ）を1〜5または null で保存する。`heso`（ヘソ）は `dailyState[machineId][date].hesoRating` として日次保存する。マップボタンには表示しない。
- B1 で `payoutType` は廃止。旧データに存在する場合も読み込み時に保持しない。
- B2 で機種プリセットを追加。B5 以降は `MACHINE_PRESETS = [{ id, name, roundBalls, standardRounds, standardPayout, evSupported, spec }]` の定数テーブルで管理する。
- 初期プリセットは P大海物語5スペシャル のみ。選択時は機種名、1R玉数 140、期待値対応フラグを自動セットする。
- P大海物語5スペシャル の標準出玉は `standardRounds: 10`、`standardPayout: 1400` とする。
- B52改訂2以降、プリセットは `roundTypes` を持つ。大海5SPは `[{ id: "r10", label: "10R", balls: 1400 }]` の単一種別。複数ラウンド機はプリセット追加時に種別数ぶん定義する。
- その他（自由入力）では機種名と 1R玉数を手入力し、期待値対応フラグは false とする。

### 2.5 DailyState

台×日付で、朝一状態と閉店チェック値を保存する。

```json
{
  "dailyState": {
    "machineId": {
      "YYYY-MM-DD": {
        "date": "YYYY-MM-DD",
        "prevInvalid": true,
        "ramClear": "cleared",
        "closingSpin": 575
      }
    }
  }
}
```

- `prevInvalid` は当日だけ有効。true の台は、前日の閉店チェック値を宵越し判定・宵サイン・実効回転数から除外する。翌日は未確認に戻す。
- `ramClear` は当日だけ有効。保存値は `cleared`（ラムクリ有り）/ `not_cleared`（ラムクリ無し）/ `unknown`（判別不能）/ null（未確認）で、ラムクリ傾向の生データとして残す。翌日のマップ表示は未確認に戻るが、日付付き記録自体は残る。
- `closingSpin` は閉店チェックで入力する対象日の閉店時点回転数。翌日の宵越し判断にのみ使う。2日以上前は判定・マップ表示に使わない。
- 自分のセッション `endSpin` はセッション記録として保存するが、マップ表示・台詳細・宵越し期待値の根拠には使わない。

## 3. 保存キー仕様

v3 は以下の localStorage キーのみを使用する。

| key | 用途 | 書き込みタイミング | データ形式 |
|---|---|---|---|

| `ytv3:premigrate` | 将来のスキーマ変更時に、旧 schema の raw データを退避する | 読み込み時、保存済み `version` が実装中の `SCHEMA_VERSION` と異なり、かつ `ytv3:premigrate` が未作成の場合。B1 では schema 1 から 2、B2 では schema 2 から 3、B3 では schema 3 から 4、B4 では schema 4 から 5、B5 では schema 5 から 6、Phase 4差し戻し1では schema 10 から 11、B10では schema 11 から 12、B20では schema 12 から 13、B13/B22では schema 13 から 14、B23では schema 14 から 15、B25では schema 15 から 16、B26では schema 16 から 17、B29では schema 17 から 18、B30では schema 18 から 19、B42では schema 19 から 20、B44では schema 20 から 21、B46では schema 21 から 22、B48では schema 22 から 23、B52では schema 23 から 24、B53では schema 24 から 25、B80では schema 25 から 26、B89では schema 26 から 27、B90では schema 27 から 28、B91では schema 28 から 29、B95では schema 29 から 30 への更新時に作成対象となる | 変更前の `ytv3:data` raw 文字列 |
| `ytv3:backup:latest` | 通常保存前の直近バックアップ | `persist()` 実行時、既存の `ytv3:data` がある場合に、新しい `ytv3:data` を書く直前 | 直前の `ytv3:data` raw 文字列 |
| `ytv3:carryover` | 次セッションへ引き継ぐ持ち玉・残高の待機状態 | 終了サマリの「この持ち玉で次の台へ」押下時に作成。打ち始めウィザード確定時、破棄ボタン押下時、日付が変わった読み込み時に削除 | `{ storeId, sourceSessionId, sourceMachineId, sourceDaiNo, date, mochidama, credit, saipurei, createdAt }` の JSON 文字列 |

| `ytv3:corrupt:<ISO日時>` | 破損した `ytv3:data` の退避 | `loadData()` で `ytv3:data` が JSON として読めなかった場合に作成。自動削除しない | 破損していた `ytv3:data` raw 文字列 |
| `ytv3:running:sticky` | 稼働中ヘッダの固定表示設定 | 固定ON/OFF切替時 | `"on"` または `"off"` |
| `ytv3:islandFilter` | 店ごとの「機種・コーナーを選ぶ」絞り込み状態 | 島/マップすべての選択時 | `{ [storeId]: "map:<mapId>" | "island:<mapId>:<index>" }` の JSON 文字列 |

### 3.1 容量予算記録

`data.meta` に以下を持つ。

- `lastSaveChars`: 直近保存時の `JSON.stringify(data).length`
- `sampleSessionChars`: Session 1 件の `JSON.stringify(session).length`
- `sampleMachineChars`: Machine 1 件の `JSON.stringify(machine).length`
- `mapLayoutChars`: 現在の MapLayout 1 件の `JSON.stringify(layout).length`
- `schemaBudgetNote`: 容量予算の注記

実装上、画面下部にも保存キー、現在保存 chars、フロアマップ chars、台データ 1 件 chars、セッション 1 件 chars、引き継ぎ chars、マップ退避 chars を表示する。

B5 実測値:

- schema 6 Store 1 件サンプル（`lendRate`、`exchangeRate`あり）: 122 chars
- schema 6 空フロアマップ: 14 chars (`{"islands":[]}`)
- schema 6 台データ 1 件サンプル: 151 chars
- schema 6 セッション 1 件サンプル（`carriedFromSessionId`、normal/yutime 投資各1件、`yutimeEnterTime`あり）: 699 chars
- `ytv3:carryover` 1 件サンプル: 203 chars

## 4. 派生値

保存せず表示時に計算する。

- 投資レコードは `phase: "normal" | "yutime"` を持つ。既存の `phase` なし投資は読み込み時に `normal` として扱う。
- 遊タイム突入後に追記された投資は `yutime` phase として保存する。
- 現金投資の玉換算は `投資金額 / store.lendRate`。
- 通常消費玉 = 開始持ち玉 + 通常 phase 投資玉換算 - 遊タイム突入玉。突入なしの場合は当選時残り玉を引く。
- 非パーソナル店、遊タイム突入玉未入力、または当選時残り玉未入力の場合は投入玉ベースにフォールバックする。
- `startMochidama === null` のセッションは回転率を算出せず、台の参考回転率集計から除外する。持ち玉なし現金スタートは `0` を入力する。
- 当選時残り玉が未入力で、プリセット機種かつ `hitCount` と `endTotalBalls` がある場合は標準出玉で概算する。
- 概算獲得出玉 = `hitCount * standardPayout`。ただし `totalRounds` が入力済みなら `roundBalls * totalRounds` を優先する。
- 概算残り玉 = `endTotalBalls - 概算獲得出玉`。負数は 0 にクリップする。
- 概算を使った回転率・獲得出玉には「概算」を表示する。台の参考回転率には概算セッションも含め、台詳細で「概算◯件を含む」と注記する。
- セッション回転率 = 通常回転数 / 通常消費玉 * 250
- 台の参考回転率 = セッション群の通常回転数合計 / 通常消費玉合計 * 250
- 遊タイム玉減り = 遊タイム突入玉 + yutime phase 投資玉換算 - 当選時玉数。当たらず終了の場合は終了時玉数を引く。
- 差玉 = 終了時玉数 - (開始持ち玉 + 全投資玉換算) + 残保留増減。
- 換算収支 = 差玉 * `(100 / store.exchangeBalls)`。
- R数ベース出玉 = `roundBalls * totalRounds`
- 1回あたりR数ベース平均出玉 = `roundBalls * totalRounds / hitCount`

## 4.1 自動ラベル

セッションの日付から以下を都度計算する。保存はしない。

- 曜日: 月曜日から日曜日
- つく日: 日付の一の位から `1のつく日` から `0のつく日`
- ゾロ目日: 11日、22日

手動のイベントメモは店独自イベントだけを登録する。フィルタでは自動ラベルと手動イベントメモを合わせて判定する。

## 5.3 B3 操作更新

- ウィザードは画面上部寄せとし、ボタン順を「次へ」「スキップ」「戻る」にする。
- ウィザードの数値入力では Enter/確定キーを「次へ」として扱う。textarea は Ctrl+Enter / Cmd+Enter のみ次へにする。
- 稼働中画面に `+500円`、`+125玉` のワンタップ投資ボタンを置く。直接入力も残す。
- 投資履歴は追記単位で表示し、各行を削除できる。削除時はカード残高・再プレ残りも再計算される。
- 開始時のカード残高・再プレ残りが未入力の場合は「未入力」と表示し、残高連動は行わない。
- 遊タイム突入時は `yutimeEnterTime` を保存し、その後の投資は遊タイム中投資として記録する。
- ヤメ入力の最初に「大当たりあり」「当たらず終了（遊タイム抜け含む）」を選ぶ。当たらず終了は `hitCount = 0` として保存する。
- セッション確定後はサマリカードを表示し、「台帳で見る」から当該記録へ移動できる。

## 5.4 B4 持ち玉引き継ぎ

- 引き継ぎは終了サマリの「この持ち玉で次の台へ」を押した時だけ発生する。
- 引き継ぎ待機状態は `ytv3:carryover` に保存し、同日内のページ再読み込みでも残す。
- 日付が変わった `ytv3:carryover` は読み込み時に削除する。日またぎ引き継ぎはスコープ外。
- フロアマップ上部に「引き継ぎ中」バナーを表示し、持ち玉、カード残、再プレ残、元台番を示す。
- 「引き継ぎを破棄」で `ytv3:carryover` を削除する。
- 打ち始めウィザードでは、持ち玉、カード残高、再プレ残りをプリセットする。元が未入力だった項目は空欄のままにする。
- 引き継ぎ値はウィザード内で手修正できる。
- ウィザード確定時に `carriedFromSessionId` を保存し、`ytv3:carryover` を削除する。
- 台帳には `carriedFromSessionId` をもとに「⇐ 台◯◯から続き」を表示する。

## 5.5 B5 デバッグ修正

- `ytv3:data` が破損 JSON の場合は、初期状態へフォールバックする前に `ytv3:corrupt:<ISO日時>` へ raw 文字列を退避する。
- 破損退避時は起動時に「保存データが読み取れなかったため退避しました」と表示し、フッターに「破損退避データあり」を出す。
- `persist()` は `lastSaveChars` を計上してから 1 回の `localStorage.setItem()` で保存する。
- 店ごとに貸玉レートと交換玉数を持つ。店追加・店設定から編集できる。
- ウィザードの「戻る」は、現在ステップの入力値を保存してから前ステップへ戻る。

## 5.6 Phase 3 フロアマップへのデータ表示

- フロアマップの台番ボタンは、台番、参考回転率、前日ヤメ回転数を縦3段で表示する。
- 参考回転率は、フィルタ適用後の完了セッションを `machineId` でグループ化して集計する。マップ描画時は `buildMachineStatsMap(filteredSessions())` を使い、計算量を O(セッション数 + 台数) に抑える。
- 参考回転率は累計加重平均（通常回転数合計 / 通常消費玉合計 * 250）。概算セッションを含む台は末尾に `≈` を付ける。
- 参考回転率の色分け閾値は `RATE_THRESHOLDS = { good: 17.0, bad: 15.0 }`。期待値対応プリセットかつサンプルありの場合のみ、17.0以上を緑、15.0未満を赤、15.0以上17.0未満を既定色で表示する。将来、設定画面化を検討する。
- 稼働中のセッションがある台には「稼働中」バッジを表示する。
- イベントフィルタ選択中は「絞り込み中」バッジと解除ボタンを表示する。該当セッションが0件の台は全期間値へフォールバックせず `-` を表示する。
- 台詳細ポップアップには、前回ヤメ回転数と日付、平均出玉、遊タイム玉減り平均を表示する。フィルタ適用中は、統計が絞り込み後の記録だけで計算されていることを明示する。
- Phase 3 は表示・集計ロジックのみの変更で、schema は 6 のまま。容量予算の増分はなし。
- 性能確認: ミコト環境の headless Chrome で 200台 / 1000セッションのマップ描画を確認し、タブ切替から最終台ボタン表示まで 1371ms。

## 5.7 P3追補 二重稼働の防止

- 同一店に `status: "active"` のセッションが存在する状態で別セッションを開始しようとした場合、開始前に確認ダイアログを表示する。
- ダイアログには「台○○がヤメ入力されていません。」と表示し、「台○○のヤメ入力へ」「そのまま新しく開始」「キャンセル」を選べる。
- 「台○○のヤメ入力へ」は稼働中画面へ移動し、既存activeセッションのヤメ入力を開く。
- 「そのまま新しく開始」を選んだ場合は旧activeを残すが、開始完了後は新しいactiveセッションを操作対象にする。
- `activeSession()` は、同店のactiveセッションを `updatedAt` / `createdAt` の新しい順で扱い、通常は最新activeを返す。画面上で切替済みの場合は選択中のactiveを優先する。
- 複数activeがある場合、稼働中画面の上部に「他に稼働中の記録があります」を表示し、台番ボタンで操作対象を切り替えられる。
- 引き継ぎ待機中でもactiveガードを優先して表示する。通常の引き継ぎは終了済みセッションから発生するため、実運用では競合しにくい。
- P3追補は画面状態と開始ガードのみの変更で、schema は 6 のまま。容量予算の増分はなし。

## 9. B6 実戦フィードバック反映

### 9.1 スキーマ

- schema は 7 とする。
- Session に `currentSpin` を追加する。打ち始め確定時は `startSpin` を初期値として入れ、以後は稼働中パネルの +1/+3/+5/+10 カウンタで更新する。旧データは読み込み時に `startSpin` を補完値として扱う。
- 投資レコードに `spinAt` を追加する。投資追記時点の `currentSpin` を自動保存し、履歴には「412回転時」のように表示する。旧データは `spinAt: null` として扱う。
- MapLayout の島ごとに `leftPresetId` / `rightPresetId` を追加する。島ビルダーの左列/右列に設定された機種プリセットを保持する。
- 稼働中カウンタの undo スタックは画面操作用の一時状態であり、localStorage には保存しない。

### 9.2 フロアマップ

- マップ画面は「台を探す」を上、「フロアマップ作成」を下に配置する。
- フロアマップ作成は折りたたみ式にし、既定は閉じる。マップ未定義の店、または店追加直後だけ開いた状態にする。
- 列単位の機種設定は、未設定台へ自動適用する。機種名、1R玉数、プリセット、台メモ、期待値対応フラグのいずれかがある台は個別設定済みとみなし、確認なしでは上書きしない。
- 列機種を変更して個別設定済み台へ反映する場合は、「この列の台◯台の機種を◯◯に更新しますか？」で確認する。
- フロアマップから外れた台と過去セッションは削除しない。増台・減台後も台帳と集計の履歴として保全する。

### 9.3 稼働中パネル

- 稼働中画面の上部に固定パネルを置き、台番/機種、現在回転数、再プレ残、カード残、持ち込み合計、概算回転率、投入合計を常時表示する。
- 現在回転数は +1/+3/+5/+10 で加算する。元に戻すは直近20件程度の加算操作を取り消す。
- 再プレ残の横に +125玉、カード残の横に +500円を置く。投資追記と残高連動は従来どおり行う。
- リアルタイム概算回転率は `(currentSpin - startSpin) / 通常投入玉 * 250` とする。持ち玉未入力、開始回転数未入力、通常投入玉0以下の場合は表示しない。
- 投資履歴は直近5件を表示し、それ以前は「過去◯件を表示」で展開する。

### 9.4 表示・操作

- 当選ウィザードの当選回転数初期値は、対象セッションの `currentSpin` とする。他セッションの値を参照しない。
- 「セッションサマリ」は「戦果報告」に改名する。
- フィルタUIは、店イベントを常設、当日該当の曜日/つく日だけを常設、その他の日付・曜日を折りたたみに分ける。クリアボタンは全チェックを解除する。
- 台帳の「記録の修正」には「この記録を削除」を置く。削除は2段階確認とし、稼働中セッションも削除可能とする。

## 10. B6差し戻し1回目

- schema は 8 とする。

## 11. B7 稼働中パネル完成形

- schema は 9 とする。

- schema 9 Session 1件サンプル（`source` 付き3ソース投入、`charges` 1件）: 870 chars

## 12. B8 稼働中パネル「実践モード」

- schema は 9 のまま。B8は表示・操作導線の再構成であり、保存データの追加は行わない。
- 稼働中画面は1枚パネル構成とし、台番/機種、固定ON/OFF、現在回転数、ライブ回転率、回転数加算、持ち玉、再プレ残、カード残、入金、累計投入、累計回転、遊タイム突入、大当たり、ヤメ、履歴を同一パネルにまとめる。
- ライブ回転率は `(currentSpin - startSpin) / 累計投入玉 * 250` で表示する。遊タイム突入後は遊タイム突入玉も同じ行に小さく表示する。
- 投入ボタンは残高が減る操作として `-125玉` / `-500円` 表記にする。内部処理はB7の `source` 付き投入と同じ。
- 再プレ残が0になった場合は「再プレ使い切り」チップへ自動的に畳む。チップをタップすると再プレ残の行を再表示できる。持ち玉行は0でも表示を維持する。
- 持ち玉、再プレ残、カード残、現在回転数は値部分をタップして修正する。B7の直接入力ボタン3種は撤去する。
- 稼働中パネルには差玉・換算収支・含み損の表示を置かない。損失回避バイアスにより稼働中の含み損表示は続行判断を歪めるため、稼働中は累計投入だけを中立情報として表示し、差玉・収支は戦果報告でのみ表示する。
- 履歴は既定で畳み、展開時は最新上に並べる。投資行には、その投資時点の累計投入玉、累計回転、回転率を表示する。入金行は投資ではないためスナップショットを付けず、時刻のみ表示する。
- 「終了入力」の画面文言は「ヤメ」「ヤメ入力」に統一する。
- B8は表示のみの変更のため、容量予算の増分はなし。

## 13. B9 大当たり入力の明確化

- schema は 10 とする。
- Session に `startTotalHits` / `endTotalHits` を追加する。どちらも null 許容で、旧セッションは読み込み時に null 補完する。
- 打ち始めウィザードに「データカウンタの累計大当たり回数」を追加する。台の本日累計大当たり回数を記録し、ヤメ時の差引計算に使う。

- 当選ウィザードは初当たりの瞬間だけを記録する画面であることを説明する。大当たり回数と出玉は、連チャン後にヤメ入力でまとめて記録する。

## 29. B26 台帳の再設計と開始時期待値の記録

- ヤメ入力（大当たりありの分岐のみ）に `累計獲得出玉` を置く。初期値は当選ごとの `actualBalls` 合計（無ければ空欄）。当選ごとの入力は道中の経過を見るための任意入力という位置づけに変わる。
- 実測出玉合計の採用順位は `sessionActualBallsTotal()` に一本化する。ヤメ入力の累計値が0より大きければそれを採用し、空欄なら当選ごとの `actualBalls` 合計、それも0なら `null`。1R平均（`合計 ÷ 合計R`）、戦果報告の獲得出玉、期待値エンジンの実測平均（`合計 ÷ 当選件数`）はすべてこの採用値を参照する。
- 実測平均はセッション単位で集計する。累計値があるセッションは `累計 ÷ そのセッションの当選件数`、無いセッションは従来どおり当選ごとの実測値を使い、両者を合算して平均する。当選ごとが未入力でもヤメの累計だけで実測平均に載る。
- `derived.hitBalls`（玉数差から求める獲得出玉）と収支計算には手を入れない。戦果報告の獲得出玉表示だけ、採用値があるときは `（実測）` を付けてそちらを優先する。
- 期待値判定の根拠に内訳行を足す。`投資 約◯円に対し期待値 ◯円（機械割 ◯% ＝ 期待値÷投資額+100%） ／ 消化時間 ◯h（通常◯h＋当選◯h＋電サポ◯h） ／ 通常時◯回転/h想定`。投資額は機械割の分母と同じ `normalCostYen`（持ち玉ぶんの玉単価換算＋現金ぶん）を使う。
- 消化時間は仕様書の2区分（通常・電サポ）ではなく3区分で出す。拘束時間は `通常 + 当選 + 電サポ` の合計であり、2区分では「合計が拘束時間と一致すること」を満たせないため。当選消化時間は `当選回数 × secPerHit`。

## 79. B91 残保留込みの引き戻し計算

- schema は 29 とする。プリセットに `holdSpins`（時短抜け後の残保留回転数）を追加し、`agnes-pe` / `umi-sp5` とも既定5。旧データは既定5で補完する（既定値変更は意図した補正）。0にすると従来と完全に同じ値に戻る。
- 当り後の時短が終わったあとに回る残保留（約5個）は玉代ゼロで抽選を受ける。現行は時短回数だけで引き戻しを計算していて、この分が抜けていた。
- st-certain（アグネスPE）: 各時短L（15/40/90）の引き戻し率を `rebound(pLow, L + holdSpins)` にする。継続率は 57.7%→59.8%、平均連チャンは 2.366→2.488 連。
- 確変ループ（大海5SP）: `r100` / `r200` / `r350` をそれぞれ `100 + hold` / `200 + hold` / `350 + hold` で判定する。遊タイムの駆け抜け後にも残保留が回るため `r350` も対象にする。
- 残保留の回転は**玉代ゼロ**（投資玉に入れない）、**電サポではない**（時短・遊タイムの玉減りレートを掛けない）、時間だけ通常時速で計上する。電サポ回転数（`expectedJitanFastSpins` など）は時短枠のみのままで、残保留は `expectedHoldSpins` として別に持つ。
- 確変ループ側の残保留回転は、電サポ回転と同じ2元連立（初当り発 / 時短中当り発）に右辺 `normal × (1-p)^L × finiteExpectedSpins(p, hold)` を入れて解く。遊タイム駆け抜けぶんは `pReach × (1-p)^yutimeJitan × finiteExpectedSpins(p, hold)` を足す。
- 機種別設定に「時短抜け後の残保留（回転）」を追加。0で考慮しない。
- 検算: アグネスPEの等価ボーダーは 1R実質105/100/90玉で 16.9/17.8/19.7 → **16.1/16.9/18.8**。記事代表点は 1R100玉・カウンター150・17回転で +1,304 → **+1,569円**、カウンター30・16回転で −448 → **−182円**。大海5SPは既定設定で全点 **+300円**（平均連 3.045→3.099 × 1,400玉 × 4円）。
- 引き戻しと残保留回転はモンテカルロ（30万〜50万試行）で両機種・hold=0/5 とも照合済み。テストにも hold=5 のMC照合を常設した。

## 80. B93 判定ラベルを時給基準にする

- schema 変更はない。`EV_THRESHOLDS`（期待値2,000円/0円）を廃止し、`DEFAULT_HOURLY_THRESHOLD_YEN`（既定2,400）を新設する。しきい値は `data.meta.hourlyThresholdYen` に全店共通の1値として保存し、セッションのスキーマには入れない。
- 判定は「打てる＝時給がしきい値以上」「微妙＝期待値が0円超でしきい値未満」「打てない＝期待値が0円以下」。拘束時間が0などで時給が出せないときは期待値の符号だけで微妙／打てないを返す。
- 記事で宣言した基準（スロ機械割105%相当＝時給約2,400円）に揃えるための変更。**長い拘束で期待値は大きいが時給が低い台は「打てる」から外れ、短い拘束で効率のよい台が新たに「打てる」に入る**。これは意図した入れ替わりで、判定パネルの根拠行に「判定基準：時給◯円以上で打てる」を常時表示して基準が見える状態にする。
- 期待値・時給・機械割の数値そのものは変えない。ラベルの分岐だけの変更。稼働中パネルや打ち始め判定も同じ `evJudgment()` を通るため自動で揃う。

## 81. B94 実機と照合するための表示

- schema 変更はない。表示だけの変更で、保存データも数値も変えない。
- 台番／機種の共通ヘッダを `machineContextLine(session|machine)` で1箇所化し、判定パネルの見出し直下と9つのモーダル（当選ウィザード／ヤメ入力の分岐と入力フォーム／戦果報告／現在回転数をリセット／現在回転数を修正／遊タイム突入／同じ台で続行／記録の修正・削除）に出す。書式は稼働中ヘッダと同じ `台104 ／ 機種名`。
- 稼働中パネルの現在回転数の横に状態バッジを出す。通常時／遊タイム中／当り後（時短消化中）の3種で、「当り後」のときは現在回転数の横に「リセット前」を添える。従来の「遊タイム中の投資として記録されます」は状態の二重表示になるため、投資の扱いだけを述べる文言に変えた。
- 状態は既存項目から導出する。遊タイム中は `isYutimeInvestmentPhase()`、当り後は「当選記録がある」かつ「現在回転数が当選回転数以上」。当選ウィザードは当選回転数の初期値に現在回転数を入れるため、記録直後は必ず一致して当り後になり、リセット（0／時短回数）を選ぶと下回って通常時へ戻る。
- **制約**: リセット有無を保存していないため、リセット後に当選回転数を超えるまで回すと再び「当り後」と表示される。同じく、実機の表示に合わせて当選回転数だけを大きく修正した場合は「通常時」のままになる。厳密にするならリセット時刻をセッションに1項目持たせる必要があり、B94では「保存項目を増やさない」制約を優先した。
- 入力欄には「（実機：◯◯）」の統一書式で照合先を書く。現在回転数・開始時点の累計大当たり回数・前日ヤメ回転数・当選回転数・残り持ち玉・現在回転数のリセット・ヤメ回転数・終了玉・累計獲得出玉の9箇所。

## 82. B95 通常消費玉のツール追跡持ち玉差分化

- schema は 30 とする。セッションに `hitTrackedBalls: number | null` を追加し、旧データは `null` 補完する。当選ウィザードを開いた時点でツールが表示している持ち玉（`deriveBalances().mochidama`、残り持ち玉入力欄の初期値）を保存する。
- B85の台上差 `開始持ち玉 + 通常phase現金/再プレ玉換算 − スナップショット玉` は、当りで持ち玉が増えた後の通常時では基準が古く成立しない。実例として タップ1,250玉に対し台上差5,861玉・回転率3.8 が算出された。
- tapMode かつ `hitTrackedBalls` があり、かつ遊タイム突入玉が無い場合、通常消費玉は `通常phaseのタップ合計 − (hitRemainBalls − hitTrackedBalls)` とする。周回数に依存せず成立する。

## 83. B97 カウンター基準と内部回転数のズレを修正

- schema 変更はない。保存データの形も値も変えない。入力値の解釈だけを直す。
- プリセットの `spec.tenjo` は内部低確の解析値（アグネスPE＝239、大海5SP＝950）だが、ユーザーが入力する現在回転数はデータカウンターの表示値（アグネスPEは250回転で遊タイム突入）。両者を無変換で繋いでいたため、アグネスPEの判定が11回転ぶん甘い側にずれていた。
- 期待値エンジンのプリセット `spec` に `counterOffset`（データカウンター表示 − 内部低確回転数）を追加する。`agnes-pe` は 11、`umi-sp5` は 0。**この数値の出所はここ1箇所だけ**とし、`yutime-v3.html` も `yutime-calc.html` も `counterOffsetForPresetId()` 経由で参照する。実測で250でなかったと分かった場合はこの1箇所を直せば記事・v3・calcが揃う。
- `engineSpinFromCounterSpin(counterSpin, presetId)` = `max(0, カウンター値 − counterOffset)`。`calculateMachineExpectation()` はエンジンへ渡す直前にこれを通す。カウンター0（ラムクリア後）は内部0回転＝残り239回転になり、記事の前提と一致する。
- 天井までの残り回転数を出している箇所（`remainingSpinTextFromEffectiveSpin`、`runningYutimeRemaining`、`transferSummaryForSession` の想定回転数・残り回転数）はすべて `remainingSpinsFromCounterSpin()` に統一し、カウンター基準の残りを表示する。`result.spinsToTenjo` は換算後の値なので一致する。
- `yutimeEnterSpinForRate()`（前日ヤメ回転数から遊タイム突入回転数を推定する）も同じ根の誤りだったので直した。前日ヤメ回転数も突入回転数もカウンター基準なので、`tenjo + counterOffset` から引く。アグネスPEで11回転ぶん少なく見積もっていた。
- 検算: アグネスPE・カウンター150・回転率17・1R実質100玉・等価・現金 → **+1,807円 → +1,569円**（記事v5と一致）。カウンター0 → 残り239回転。大海5SPは `counterOffset: 0` なので既存の基準点（434回転・想定回転数425・残り330など）が不変であることをテストで固定した。
- `yutime-calc.html` のページ固有だった −11 の直書きは廃止し、エンジンの `counterOffset` を読む形にした。`tests/yutime-calc.test.js` でページ側にずれの数値が書かれていないことも検証する。
- 制約: `MACHINE_PRESETS` の `agnes-pe` は spec/defaults をエンジンと別に持つ重複が残っている（B91以前からの状態）。`counterOffset` はエンジン側だけに置き、参照は必ずエンジン経由にすることで二重管理を避けた。

## 84. S8 獲得出玉の累計を連チャン単位にする

- schema 変更はない。保存項目（`hits[].actualBalls` / `sessionActualBalls`）の形は変えず、入力値の解釈と採用順位だけを直す。
- 実機のデータカウンターが表示する獲得出玉は「その連チャンの累計」で、時短が終わって通常時に戻ると0に戻る。B88はこれをセッション累計として扱っていたため、2回目の初当りで入力値が前回までの合計を下回り、「前回までの累計を下回っています」の警告が出て今回分が0で保存されていた。結果として実測出玉が過少になり、1R平均が実態より小さく出る。
- 累計の範囲を連チャン＝**同じ区間に紐づく当たり群**（`hits[].segmentId`。S4/C-4の「今回の連チャン」と同じ切り出し）にする。`chainSegmentIdForHit()` / `chainActualBallsBefore()` を追加し、今回分 ＝ 入力値 − 同じ連チャン内のそれ以前の合計とする。下回り警告も同じ連チャン内での比較になる。時短抜けで次の区間が開くため、連チャンの区切りは区間の境界と一致する。
- 検算: 連チャン①（4R→1,380／6R→2,800）→ 時短抜け → 連チャン②（4R→1,380／4R→2,600）で、今回分は 1,380／1,420／**1,380**／1,220。#3 は連チャンが変わるので下回り扱いにしない。セッション合計5,400玉・合計18R → **1R当たり300玉**。
- セッションの実測出玉合計（`sessionActualBallsTotal()`）は**各当選の今回分の単純合計**に一本化する。連チャンをまたいでも加算で正しい。B90で入れた `sessionActualBalls` は、当選ごとの記録が無い旧データのフォールバックとしてだけ読む。
- ヤメ入力（大当たりありの分岐）の `累計獲得出玉` 欄は削除する。実機がその数字を表示せず、照合できない入力を求めていたため（B94の原則に反する）。`sessionActualBalls` フィールドと `normalizeData()` の補完は旧データのために残し、ヤメ入力では上書きも消去もしない。
- 大当たり履歴の累計出玉表示（`hitHistoryRows()`）と、修正フォームの初期値も連チャン単位に揃える。区間ごとの見出しの下で0から積み直すため、カウンターの表示と同じ読み方になる。
- 文言: 大当たり登録の入力欄を「この連チャンの累計出玉（実機：データカウンター）」に、ヒントを「いま表示されている、この連チャンの累計出玉を入力してください。時短が終わると0に戻ります。前回の入力との差が、今回の当たりの出玉になります。」に変更。
- 回帰: 保存されているのは今回分（`actualBalls`）なので、当選ごとの記録があるセッションは合計値が不変。ヤメ累計だけの旧データはフォールバックで従来値のまま。**唯一値が動くのは `sessionActualBalls` が当選ごとの合計と食い違う旧データ**で、その場合は当選ごとの合計（＝出典1つ）を採る。
- `netBallsPerWinInfo()`（期待値の実測平均＝合計 ÷ 当選件数）の採用順位はS8では変えていない。既存データの期待値を動かさないことを優先したため、ヤメ累計を持つ旧セッションは従来どおりそれを使う。新規セッションは `sessionActualBalls` を持たないので当選ごとの実測に落ちる。
