# 東京喰種 第1号 段2（稼働日誌の集計）仕様書 v0.1

- 作成：シオン／2026-11-28（JST）
- 根拠：骨格書 `docs/specs/tokyoghoul-nisshi-stats-skeleton-v02.md`（2026-11-28 夢爽裁可）§3〜§8、段1 仕様書 `tokyoghoul-stats-1-spec-v01.md`
- 基準：main `01dcb42`（段1 反映済み）
- 対象：新規 `js/play-stats.js`、`tools/nisshi/index.html`（＋検証）。tools/rec は**触らない**

> 要するに：稼働日誌の分析で機種「L東京喰種」を選ぶと、東京喰種の集計（通常G・CZ確率と成功率・AT初当たり確率と契機・有馬・実差枚・勝率）と、CZ1回ずつの表が出るようにします。台の詳細では、その台の集計と、前回状況の補足・訂正ができます。集計は保存せず、表示のたびに計算します。

## 0. 絶対ルール

1. 集計値はどこにも保存しない（導出値は保存しない原則）。保存が増えるのは、夢爽が台の詳細で訂正したときの `statsFix` だけ
2. 既存の分析（収支・円・月別・機種別・店別・狙い方・タグ）の数字と見た目を変えない。東京喰種の集計は、機種を「L東京喰種」に絞ったときだけ足す
3. 有効にする機種は `js/play-stats.js` の一覧で決める。今回は `tokyoghoul` だけ。一覧にない機種は何も出さない（推定表示もしない）
4. 一次データ（取り込んだ rec の記録）は書き換えない。訂正は日誌の `statsFix` に置く
5. IndexedDB の版（`DB_VERSION=2`）・ストアは変えない
6. 画面の文言に「アルゴリズム」「事後確率」などの内部・統計用語を使わない（§9-94）。ツール内部の扱いを書いた文（「〜には使いません」）も使わない

## 1. 共通部品 `js/play-stats.js`（新規）

DOM に触れない純粋な関数だけを置く。日誌は `<script src="../../js/play-stats.js?v=20261128">` で読む。Node からも読めること（検証で直接呼ぶ）。

### 1-1. 公開するもの

```js
window.PlayStats = {
  enabled: ['tokyoghoul'],          // 有効にする機種定義
  defs: { tokyoghoul: {...} },      // 機種ごとの定義（§2）
  defFor(play),                     // 台 → 定義 or null
  extract(play, def),               // 1台の集計（§3）
  aggregate(rows, def),             // 台の一覧 → 合計（§4）
  czRows(rows, def),                // CZごとの表・失敗の次（§5）
  effectiveSetup(play),             // 着席項目（rec の値に statsFix を重ねたもの）
};
```

- 名前・形は例。ミコトが調整してよい（報告に明記）。ただし保存項目名 `statsFix` は変えない

### 1-2. `defFor(play)`：対象の判定

| 台 | 判定 |
|---|---|
| `play.source==='rec'` で `play.raw.machineId` が有効一覧にある | その定義 |
| `play.source==='rec'` で `play.raw.envelope?.payload?.machineDef` が有効一覧にある（JSON取り込み） | その定義（§6 で `raw.machineId` も入るようにする） |
| 上以外（汎用で記録した旧「東京喰種」、簡易収支だけの台、ほかの出どころ） | `null`（集計の対象外） |

- 機種名・mid（s0001）だけでは対象にしない（構造化された記録がないため）。ただし「対象外◯件」の件数には、機種が「L東京喰種」に名寄せされる台を数える

## 3. `extract(play, def)`：1台の集計

### 3-1. 通常時の区間（骨格書 §4 の状態遷移表）

ログ（`play.events`）を頭から読み、`通常時`／`当選中` の2状態で区切る。

| 出来事 | 判定 | やること |
|---|---|---|
| 開始 | — | 状態＝通常時、始点＝`raw.startRealG`（無ければ0） |
| `hitStart`（状態＝通常時） | — | 終点＝その行の `realG`。区間G＝終点−始点を足す。状態＝当選中 |
| `hitStart`（状態＝当選中） | CZ成功→AT、EP→AT、有馬、死神→AT など | 区間は動かさない |
| `hitEnd` で行の `mode==='normal'` | 通常時に戻った | 状態＝通常時、始点＝`toG.realG`。`toG` が無ければ定義の推定値を使い「推定あり」 |
| `gFix`（G数を直した） | — | 区間Gには足さない。「補正あり」 |
| 終わり（状態＝通常時） | — | 終点＝`raw.realG`（終了時のデータカウンタ）。区間Gを足す |
| 終わり（状態＝当選中） | ヤメ中の当選 | 区間は足さない。その当選の成否は「不明」 |

- 区間Gがマイナスになったら、その台の通常Gは「G数の不整合」として `normalG=null`（合計から外し件数表示）
- 液晶Gは区間には使わない

### 3-2. 数えるもの

| 値 | 数え方 |
|---|---|
| CZ当選（種別ごと） | `hitStart.hit` が CZ |
| CZ成功／失敗 | その CZ の `hitEnd.result`（"成功"／"失敗"）。終わらずにヤメ＝不明 |
| EP当選 | `hitStart.hit` が EP |
| AT初当たり | `hitStart.hit==='AT'` かつ契機が `死神後` 以外。契機で分類 |
| 有馬ジャッジメント | 当選回数・成功・失敗（CZには入れない） |
| 有馬失敗後のCZ | `hitStart.afterMark==='有馬失敗後'` の CZ の件数（内訳） |
| 実差枚 | `raw.money.endMedal` − `startMedal` − 再プレイ合計 − round(現金投資 ÷ 1000 × 貸枚数)。貸枚数は `raw.cond.lend`、無ければ `raw.lend` |
| 実差枚が出せない | `endMedal` が null、または現金投資があり貸枚数が無い → `medalDiff=null`（未確定） |

- 1台の結果に、印（`estimated`・`corrected`・`inconsistent`）と条件（`effectiveSetup`）を含める
- 「CZ成功→AT」の `hitStart` に付く契機は rec の作りでは `レミニセンス`／`大喰いの利世`／`引き戻し`。ミコトは rec のコードで実際の値を確かめ、§2 の分類で全部拾えることを報告する

### 3-3. 着席項目（`effectiveSetup`）

- rec の `raw.setup`（JSON取り込みは `payload.setup`）に、日誌の `statsFix` を項目ごとに重ねる（`statsFix` にある項目が勝つ）
- `statsFix` で「なし」にした項目は、rec に値があっても「なし」として扱う（§7 の保存形）
- showWhen を満たさない項目は捨てる（rec と同じ規則）

## 4. `aggregate(rows, def)`：合計

| 表示 | 式 | 出せないとき |
|---|---|---|
| 対象台数 | 自動の台・確定値の台（段3）・対象外の台を分けて表示 | — |
| 通常G | 合計 | — |
| CZ確率（合算・通常・上位） | 合計通常G ÷ 合計当選回数（「1/◯◯G」） | 回数0 →「—」 |
| CZ成功率（合算・通常・上位） | 成功 ÷（成功＋失敗）。不明の件数を併記 | 判明0 →「—」 |
| AT初当たり確率 | 合計通常G ÷ AT初当たり回数 | 回数0 →「—」 |
| AT契機別 | 回数（§2 の分類の順） | — |
| EP・有馬 | 回数、有馬は成功率 | — |
| 実差枚 | 合計・平均（合計 ÷ 確定台数）・勝率（プラスの台 ÷ 確定台数。±0は勝ちに入れず母数に入れる） | 確定0 →「—」。未確定の件数を併記 |
| 印の件数 | 推定あり・補正あり・G数の不整合 | — |

- 確率は合計どうしの割り算（台ごとの比率の平均にしない）
- 通常Gが不整合の台は、通常Gと確率の計算から外す。回数（CZ・AT）・成功率・差枚には入れる（件数表示で分かるようにする）
- 段3 の確定値の台は、ここに入る形だけ用意する（`meta.statsConfirmed` を読む。段2では中身が空でよい）。同じ sessionId の自動の台があれば確定値を使い、自動の台は数えない

## 5. `czRows`：CZごとの表・失敗の次

- 対象は自動の台だけ（確定値の台は CZ1回ずつの情報がない）
- **CZごとの表**：CZ当選1回ずつを「種別 × 契機 × 規定G数」で分け、当選回数・成功・失敗・不明。規定G数が無い行は「規定G数：—」
  - 当選時の液晶G は、行ごとの一覧（§8 画面）で見られるようにする（表の分け方には使わない）
- **失敗の次**：CZ失敗のあと、同じ台の中の次の当選（CZ・EP・AT直撃）の「種別・契機・規定G数・当選時の液晶G」。次が無ければ「ヤメ（通常 ◯G）」
  - 着席前の分：着席項目で前回が CZ失敗の台は、「前回CZ（契機・規定G数・液晶G）→ この台の最初の当選」を同じ表に「着席前」として足す
- 件数0の行は出さない

## 6. JSON取り込み（`envelopePlay`）の読み方

- `payload.structVer>=1` で `payload.events` が配列のときだけ：
  - `events` は `payload.events` を使う（文章の `logs` は使わない）
  - `machineId` に `payload.machineDef`、`setup` に `payload.setup`、`startRealG`・`startLcdG`・`realG`（＝`endRealG`）・`lcdG`（＝`endLcdG`）を入れて `recPlay` に渡す
- それ以外（`structVer` なし）は今までどおり。**旧JSONを取り込み直しても「更新」にならない**こと（比較 `comparable` が変わらない）
- rec から直接取り込んだ台と JSON で取り込んだ同じ台は、今までどおり同じ ID（`rec:<sessionId>`）になる

## 7. 日誌側の補足・訂正（`statsFix`）

- 台（plays）の新しい項目 `statsFix`。`PROTECTED` に追加する（再取り込みで消えない）
- 形：`{ [項目名]: 値 | null }`。`null` は「日誌で『なし』に直した」。項目が無い＝rec の値のまま
- 訂正がすべて rec の値と同じになったら `statsFix` 自体を消す
- 手で台をまとめる（`mergeManual`）とき、`statsFix` は残る側（target）のものを使う。target に無く other にあれば引き継ぐ
- バックアップ（書き出し・復元）に含まれる（plays ごと保存されるので追加作業はない想定。検証で確かめる）

## 8. 画面

### 8-1. 分析

- 機種の絞り込みが「L東京喰種」のとき、既存の合計・グラフの**後ろ**、「機種別」の表の**前**に「東京喰種の集計」の節を足す
  - 既存の期間・店・狙い方・タグの絞り込みは、そのまま効く
  - 節の中に東京喰種用の絞り込み：着席時の状況／開始時CZスルー（データにある値だけ選択肢にする）／前回の当選／前回CZの契機／前回CZの規定G数（◯以上・◯未満）／前回CZ当選時の液晶G（◯以上・◯未満）／前回ATの結果。数字はテンキー（既存の `prepareNumbers`）
  - 表：§4 の値。印の件数と「対象外◯件（汎用で記録した台など）」
  - 「CZごとの表」「失敗の次」（§5）。台単位の表とは見出しで分ける
  - 注記を1行：「打った台の記録から数えた値です。機種そのものの確率ではありません。」
- 絞り込みの状態は今の `page.filters` と同じ扱い（保存しない）

### 8-2. 台の詳細

- 対象の台（`defFor` が定義を返す台）だけ、既存の「狙い方・タグ」の前に「この台の集計」を出す：通常G・CZ（種別ごと・成否）・AT初当たり（契機）・有馬・実差枚・印
- 「前回状況を補足・訂正」ボタン → シート：着席項目を rec と同じ表示・連動（showWhen）で出す。初期値は `effectiveSetup`。保存で `statsFix` を作る
- 訂正がある台は「日誌で直した項目あり」と小さく出す。「rec の値に戻す」で `statsFix` を消す
